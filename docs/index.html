RFI-002 · Client B · opened 2026-10-22

PHP2Shell: critical PHP flaws (CVE-2026-109618, CVE-2026-109619)

In progress · re-checked today
Bottom line: Two critical PHP bugs let an unauthenticated attacker run code on a web server. They are now confirmed exploited and on CISA's Known Exploited Vulnerabilities list (added 26 October). Patch every internet-facing PHP system now, then check it was not compromised from 17 October onwards.

What is affected High concern
Any PHP that serves web requests: PHP-FPM, Apache mod_php (highest risk), php-cgi, FrankenPHP and LiteSpeed. Fixed in 8.5.12, 8.4.27, 8.3.36 and 8.2.35. PHP 8.1 and older are end of life, so only a vendor backport (for example a Linux distribution or Plesk build dated 21 October) protects them. PHP is also bundled inside hosting panels, appliances and products like WordPress hosting, so suppliers must be asked.
Exploitation High concern
Amazon's honeypots recorded an exploitation attempt on 17 October, four days before disclosure, and Amazon cannot explain how the attacker had the details. Details then leaked publicly on 20 October and proof-of-concept code appeared on 21 October. Cloudflare saw early attack attempts and deployed emergency WAF rules, and Patchstack reports attacks are ongoing. Some public exploit code is unverified and may itself contain malware. By 23 October BleepingComputer reported successful exploitation in the wild and Mirai botnet operators had joined the attacks, although some researchers still question how reliable the public exploits are. CISA added both CVEs to KEV on 26 October (US federal deadline 29 October). Cloudflare counted millions of attempts by 22 October. In the UK only about a quarter of exposed hosts had been patched (Infrawatch), the NCSC sent more than 50,000 warnings to UK organisations, and 32 government services were taken offline as a precaution. CYFIRMA reports a slow, low-volume scanning campaign it links to North Korea, aimed at governments, banks, airports and payment platforms.
What an attack looks like Medium concern
Very large form POSTs (about 3.5 MB field names, null bytes). PHP error log: 'Allowed memory size of ... bytes exhausted (tried to allocate ...) in Unknown on line 0'. Apache: 'AH00052: child pid ... exit signal Segmentation fault (11)'. The clearest sign of success is a web worker (php-fpm, apache2, httpd) starting a shell or connecting out. A successful exploit can return HTTP 200 with no crash, so absence of errors proves nothing.
Network detection Medium concern
Network detection: Cisco Talos Snort rules 67359 and 67360 cover both CVEs (also in the free Community Ruleset). They can only inspect traffic they can read, so HTTPS between a CDN or WAF and the web server hides attacks from a network IDS in front of that server.
Third bug: CVE-2026-115560 Medium concern
Announced 23 October. The 21 October patches do not fix it and there will be no emergency release; the fix comes in the next regular PHP release. It needs an unusual session configuration (a non-default session.serialize_handler switched at runtime, with session upload progress on). Workaround: set session.upload_progress.enabled=0 as an administrative setting and fully restart PHP workers.
Assessment

Exploitation is confirmed and widespread. It is almost certain (95% and above) that unpatched internet-facing PHP sites will be attacked, and highly likely (80-90%) that a long tail of compromises surfaces over the coming months. A site patched after 17 October could already have been compromised, so patching alone is not enough.

High confidence. CISA KEV (catalogue 2026.10.26) and the CVE records were checked directly on 27 October.

Recommended actions
  1. Find every PHP system, internet-facing first, including PHP bundled in third-party products and hosting.
  2. Upgrade to 8.5.12, 8.4.27, 8.3.36 or 8.2.35 (or later) and restart all PHP workers. For 8.1 and older, get written confirmation of a vendor backport or migrate.
  3. Apply the CVE-2026-115560 workaround where practical: set session.upload_progress.enabled=0 administratively (for example php_admin_flag in the PHP-FPM pool) and fully restart PHP workers, then apply the next regular PHP release when it ships.
  4. If an internet-facing system cannot be patched quickly, put a WAF block on oversized POST bodies or take it offline (NCSC advice).
  5. Hunt for compromise since 17 October: web workers spawning shells, new PHP files in web roots, outbound connections from web servers, and the memory and crash errors above.
  6. Google SecOps: confirm the Mandiant Frontline Threats curated rule pack is enabled (23 new detections), and check Emerging Threat Center entry GLOBAL.26.015 where licensed.
  7. Where the website is run by a supplier, ask them to confirm the patched version, the restart, and the result of their own log review, and to share Cloudflare security events if you want them reviewed.
Hunt queries (7)
1. Web worker starts a shell or download tool (UDM search)

Strongest sign of successful exploitation. Needs Linux endpoint telemetry (EDR or auditd) from the web servers.

metadata.event_type = "PROCESS_LAUNCH"
AND principal.process.file.full_path = /(php-fpm|php-cgi|lsphp|frankenphp|httpd|apache2)/ nocase
AND target.process.file.full_path = /\/(sh|bash|dash|zsh|curl|wget|python[0-9.]*|perl|nc|ncat|socat|busybox)$/ nocase
2. Same, as a YARA-L detection rule

Save as a rule so it alerts from now on.

rule php2shell_worker_spawns_shell {
  meta:
    description = "PHP or web worker launching a shell or download tool (PHP2Shell post-exploitation)"
    severity = "HIGH"
  events:
    $e.metadata.event_type = "PROCESS_LAUNCH"
    $e.principal.process.file.full_path = /(php-fpm|php-cgi|lsphp|frankenphp|httpd|apache2)/ nocase
    $e.target.process.file.full_path = /\/(sh|bash|dash|zsh|curl|wget|python[0-9.]*|perl|nc|ncat|socat|busybox)$/ nocase
  condition:
    $e
}
3. New PHP files written by the web server (UDM search)

Web shells dropped after exploitation.

metadata.event_type = "FILE_CREATION"
AND target.file.full_path = /\/(var\/www|srv\/www|public_html|htdocs|wp-content)\/.*\.(php|phtml|phar)$/ nocase
AND principal.process.file.full_path = /(php-fpm|php-cgi|lsphp|httpd|apache2|nginx)/ nocase
4. Exploit attempts in PHP and Apache error logs (raw log search, regex)

Needs PHP or Apache error logs ingested. Errors alone are not proof; correlate with oversized POSTs.

Allowed memory size of \d+ bytes exhausted.*in Unknown on line 0
AH00052: child pid \d+ exit signal Segmentation fault \(11\)
child \d+ exited on signal 11 \(SIGSEGV
5. Oversized POST requests (UDM search, web proxy, WAF or load balancer logs)

The out-of-memory exploit uses multi-megabyte form posts. Which byte field holds the request size depends on the log source.

metadata.event_type = "NETWORK_HTTP"
AND network.http.method = "POST"
AND network.sent_bytes > 1000000
6. Outbound connections from web workers (UDM search)

Reverse shells and downloads. Exclude your own ranges and known update servers.

metadata.event_type = "NETWORK_CONNECTION"
AND principal.process.file.full_path = /(php-fpm|php-cgi|lsphp|frankenphp|httpd|apache2)/ nocase
7. IDS alerts for the Talos PHP2Shell rules (UDM search)

Works for any Snort-based IDS feeding the SIEM, including Cisco and Meraki, where signature IDs look like 1:67359:1. Only sees unencrypted traffic.

security_result.rule_id = /(^|:)(67359|67360)(:|$)/
OR security_result.rule_name = /php2shell|CVE-2026-10961[89]/ nocase

Okta vulnerabilities

In progress · re-checked today
Bottom line: No Okta or Auth0 vulnerability is known to be exploited. The real risk to Okta customers is social engineering: phone-call phishing (vishing) that tricks staff or the help desk into handing over sign-ins and MFA.

Patch batch: September 2026 advisories Medium concern
On 8 September 2026 Okta published fixes for nine bugs in its self-hosted components, found by scanning its own code with AI. Okta reports no evidence of exploitation, and none are on CISA's Known Exploited Vulnerabilities list (re-checked 12 October, catalogue 2026.10.08). Okta's cloud service is patched by Okta; customers only need to act if they run the components below.
Active threat: vishing against Okta SSO High concern
Since January 2026, groups linked to ShinyHunters, Scattered Spider and Lapsus$ ('Scattered LAPSUS$ Hunters') have called staff and IT help desks, steering victims through fake Okta login pages in real time to capture passwords and MFA approvals. Push MFA with number matching does not stop it. Once inside Okta, they move into connected SaaS apps (Salesforce, Microsoft 365, Google Workspace) and steal data for extortion. Reported targets include financial services. Latest tradecraft (September): attackers keep access by enrolling their own Okta FastPass device, often an emulated Android phone, so a password reset alone does not remove them.
Assessment

It is unlikely (25-35%) that the September Okta bugs are being exploited at scale today, but a realistic possibility (40-50%) that exploitation follows now that details are public. It is highly likely (80-90%) that vishing against Okta-using organisations continues through the rest of 2026.

Moderate confidence. CISA KEV (catalogue 2026.10.08) and the CVE records were checked directly on 12 October; Okta's own advisory pages could not be reached and are cited from search results.

Recommended actions
  1. Check whether you run any of the listed self-hosted components and upgrade them to the fixed versions.
  2. If you used the Hyperdrive installer, rotate the OAuth client secret and clear old installer and agent logs, since they may hold secrets or SAML assertions.
  3. Move admins and help desk staff to phishing-resistant MFA (Okta FastPass, FIDO2 security keys or passkeys), then everyone else.
  4. Use Okta network zones to allow sign-ins only from expected networks and block anonymisers (VPNs, Tor, proxies).
  5. Tighten help desk checks before any password or MFA reset, for example a call back to a known number or manager approval.
  6. Alert on new Okta FastPass or authenticator enrolments, especially from emulated or unrecognised Android devices, and review existing enrolments after any suspected compromise.
  7. Watch the Okta System Log for new MFA enrolments or resets, sign-ins from new devices or locations, and new admin role grants, and alert on them.
  8. Block the Okta-themed malware URLs listed above (defanged) and warn Okta admins and developers not to download Okta tooling from unofficial GitHub repositories.

CVSS vs EPSS vs KEV

CVSS (0-10) says how bad a bug could be if exploited. EPSS (0-1, from FIRST.org) estimates the chance it will be exploited in the next 30 days. KEV (CISA's Known Exploited Vulnerabilities list) says it is already being exploited. Severity, likelihood, reality.

Think of it like this: CVSS is how deep the river is. EPSS is the chance it floods this month. KEV is: it is flooding now.
Why it matters for UK clients

Cyber Essentials requires critical and high-risk updates to be applied within 14 days. Using KEV and EPSS helps clients decide which of those to do on day one rather than day fourteen.

Enrichment tip

Never send a CVE to a client with only a CVSS score. Always add EPSS percentile and KEV status, plus whether they run the product.

The Pyramid of Pain

David Bianco's Pyramid of Pain ranks indicators by how much it hurts the attacker when you block them. Bottom to top: hash values (trivial to change), IP addresses (easy), domain names (simple), network and host artefacts (annoying), tools (challenging), TTPs: tactics, techniques and procedures (tough).

Quick quiz: Which is harder for an attacker to change: an IP address or a technique (TTP)?
Show answerA technique. TTPs sit at the top of the pyramid because changing them means changing how the attacker works.

Critical national infrastructure and NIS

CNI covers services the UK depends on: energy, water, transport, health, telecoms, finance, government and more. The NIS Regulations 2018 set security duties for operators of essential services and some digital providers, and many are assessed against the NCSC Cyber Assessment Framework (CAF). The Cyber Security and Resilience Bill is set to widen these rules, so check its current status.
